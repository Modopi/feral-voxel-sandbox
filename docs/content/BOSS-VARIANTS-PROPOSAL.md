# 후반 보스 변형 — 검토 완료, 수치·보상은 제안값

2026-10-17. Root가 네 `contentVariantId`와 행동·저장 계약을 검토했다. 정본 `bosses.json.rules.tierVariants`에 따라 대표 티어 밖 자동 배율은 계속 금지하고, 검토된 변형 ID만 별도로 등록한다. 기존 8개 보스·24페이즈·32기술과 원형 T7/T8은 보존한다. 아래는 수도원 수호자와 관측탑 파수기의 T9/T10 네 변형이며 새로운 4종 보스나 신규 에셋 완성으로 집계하지 않는다. HP·피해·EU·TTK 목표와 보상량은 모두 실제 플레이·경제 검증 전의 **제안값**이다. 신규 소환수·생명 제작·독점 재료를 추가하지 않는다.

## 공통 계산과 불변 조건

개인 비교 장구: T7 HP235/방어후배율0.62/유효DPS84, T8 275/0.58/120, T9 320/0.54/172, T10 380/0.50/245. 유효 DPS는 기존 이동·회피·저항을 반영한 **설계 목표**이므로 가동률0.65를 또 곱하지 않는다. 모든 변형 목표 TTK160초(실측 아님), 기계 기준1.6배 유효DPS는100초다. 회복 성공 시 더 길어진다.

`HP=해당티어 유효DPS×160`, `피해배율=(새장구HP/원형장구HP)×(원형방어후배율/새방어후배율)`로 원형의 한 번 맞을 때 HP 비율을 유지한다. 중립피해는 가장 가까운 정수로, 비용은 `ceil(중립피해×1.5)` EU로 계산한다. 채널은 그대로 유지한다. 기존 에너지방어·약점배율·충돌질량·크기는 바꾸지 않는다. 전체 HP가 사망 기준이며 외피 유효 타격도 HP를 줄인다. 부위파손은 기능 변화다.

수리HP는 최대HP의8%, core12%, locomotion18%, 기믹은 유효DPS×3초다. 원형 부위값이 정수 반올림되어 있어 비율을 다시 곱하는 대신 원래12/18% 계약으로 계산한다. 원형처럼 수리재2개/최대2회/5초정지/피격중단/소모재반환없음을 유지한다.

각 채널 `capacityEU=그 채널 최대기술비용×10`, `initialEU=capacityEU`, `rechargeEU=최대기술비용×4`, 공급6회/재충전4초를 유지한다. 반올림 후 yield는 실제피해/비용이다. 한 시전의 EU·피해 예산을 여러 기계부위/표적에 복제하지 않는다.

예고·active·recovery·쿨다운·사거리·형상·HP페이즈 임계·전환시간·interCastGap은 원형과 같다. 보행3.2m/s, 반응0.3초, 아바타반경.35m 검사도 같아서 최소 예고 여유는 수호자 hammer .5531초, 파수기 collapse .6531초다. 이동 변형은 **예고 이전에만** 실행하고, windup 시작 시 고정된 목표점·형상을 끝까지 유지한다. 실제 이동 경로가 막히면 재배치만 포기하고 원형의 사거리·시야·회피조건을 다시 검사한다.

## 원형과 다른 실제 행동

아래 `variantState`는 저장되는 실행 상태이며 같은 공격 순서 이름만 바꾸는 표식이 아니다. 매 완료 시전 후 한 번만 실행하고, 진행 중 시전·잔존위험·recovery와 겹치지 않는다. `pendingReposition` 최대1.5초, 접촉 시 중단, 순간이동 금지다. 추가 이동 때문에 TTK가 늘 수 있으므로160초는 검증 목표로 남긴다.

### 수호자 T9 — 측면 방어와 교대 수리

- P1: hammer 완료 후 다음 시전 전에 플레이어 방향에 수직인 좌/우3m 지점으로 교대로 이동한다. 이동 목표는 예약 시 한 번 고정한다. `sideSign`을 저장하고 다음 hammer 완료 때 반전한다. 정면 고정 표적과 달리 개인/차량 모두 사선을 조정하게 된다.
- P2: 수리 시 온전하고 미소모인 두 성소를 교대로 선택한다. 선택된 성소 ID를 저장해 재로드로 유리한 성소를 다시 고르지 않는다. 성소가 소모되면 해당 선택을 취소하고 나머지 성소 또는 원형 공격으로 복귀한다. 수리시간/노출은 원형과 같다.
- P3: 모든 기관이 노출되는 원형 상태를 유지하며 재배치를 멈춘다. 약점 보상이 명확한 마무리 구간이다.

### 수호자 T10 — 성소 상태가 이동 패턴을 끊음

- T9의 P1/P2 행동을 사용한다.
- P3: 온전한 성소가 하나라도 있으면 ray 완료 후 좌/우3m 재배치를 한 번 실행한다. 두 성소가 모두 소모/파괴되면 이동 변형이 영구 중단되고 원형 P3 고정 공략으로 바뀐다. 성소를 처리하지 않아도 HP로 처치 가능하다.
- core 파손으로 sweep가 금지되어도 hammer/ray/seal의 원형 fallback이 남는다. 기관을 부쉈다는 이유로 새 무료 공격이나 복구를 생성하지 않는다.

### 파수기 T9 — 공격 뒤 궤도 방향 전환

- P1은 원형 중앙 추적을 유지한다.
- P2: rail 또는 arc가 끝나면 원형 반경6m 궤도상의 다음 각도0.35rad 지점으로 재배치한 뒤 다음 예고를 시작한다. rail 완료마다 `orbitSign`을 반전하므로 같은 방향 추격만으로 모든 공격을 뒤에서 맞힐 수는 없다. 각 이동목표와 방향을 저장한다.
- P3는 원형 반경3m/속도.75배/전면 노출을 유지한다. 관성닻을 하나라도 처리하면 기존 ring recovery+1초에 더해 변형 재배치가 중단된다.

### 파수기 T10 — 닻으로 해제되는 양방향 기동

- T9와 같은 기술·형상 및 P1을 사용한다.
- P2와 P3에서 T9의 rail/arc 뒤 재배치를 적용한다(반경은 각 원형 페이즈값6m/3m). rail과 arc 완료마다 방향을 반전한다.
- 서쪽 닻 소모는 음의 방향, 동쪽 닻 소모는 양의 방향 재배치를 각각 금지한다. 남은 허용 방향을 사용하며 둘 다 소모되면 재배치가 완전히 중단된다. 보스·닻 상태가 저장되므로 재접속으로 금지를 풀지 않는다.
- core 파손 뒤 collapse는 모든 페이즈에서 금지하며 나머지 세 기술만 사용한다. 추가 동시 공격·무한 전격·비행 무효화는 없다.

## 공간·보상 연결 제안

수도원36×36×16m, 관측탑40×40×20m, 기존 실제 장애물·문6×5m·성소/닻 좌표를 유지한다. 재배치 목표는 방 경계1m 안쪽으로 제한하고 실제 collider sweep을 통과해야 한다. 경로가 막히면 이동을 취소하며 출구를 막는 구조물을 새로 만들지 않는다. 원형의 보호 탈출띠와 모든 공격의 회피검사를 그대로 적용한다.

보상은 기존 channel 원장·동일 인스턴스 최초처치1회만 유지한다. 추가 풀 ID 제안은 `reward_forgotten_monastery_t9/t10`, `reward_inertia_tower_t9/t10`이다. salvage/archive는 기존 풀 유지, boss 채널만 다음처럼 대체한다. 제작으로도 얻을 수 있는 기존 material이며 고유 드롭이 아니다.

| 풀 | 보스 확정재료 | 신성EU |
|---|---|---:|
| 수도원T9 | blessed_holy_iron 3 | 45 |
| 수도원T10 | saints_endurance 3 | 50 |
| 관측탑T9 | superstring_aggregate 3 | 45 |
| 관측탑T10 | cosmic_megastructure 3 | 50 |

이 보상은 기존 최종재료 생산과 비교하여 progression 담당 검토가 필요하다. 자료 없음에도 제작비와 동등하다고 단정하지 않는다. 필수 연구·재료를 발견 독점으로 바꾸지 않는다.

## 등록·저장·연결 API

- `bosses.json.variants[]`에 네 `contentVariantId`, baseBossId, tier, baselineRef, 확정 수치 override, typed behavior, rewardRef를 추가하는 안. 기존 entries[]8개는 그대로다. 새 JS모듈 없이 bosses.js 안의 검증/해석 함수로 처리한다.
- `BossSystem.spawn(baseBossId,position,{contentVariantId,tier,instanceId,arenaOrigin})`. 등록하지 않은 변형/티어/원형 조합은 여전히 거절한다. variant 생략 시 현재 원형 규칙 유지.
- `BossSystem.definitionFor(entityOrId)`가 원형+변형을 합친 읽기용 정의를 반환한다. entity.bossId는 원형 에셋·애니메이션 ID로 유지한다. tier/contentVariantId는 별도 영속 값이다. 원형 definitions Map의 내용을 변형 값으로 덮어쓰지 않는다.
- 저장: contentVariantId, variantSchemaVersion=1, encounterTier, variantState{sideSign,orbitSign,selectedRepairGimmickId,pendingReposition,lastRepositionCastId}. 원형 저장은 variant=null로 읽는다. 새 변형 상태를 구원형 HP비율로 역변환하지 않는다. 알 수 없는 변형 저장은 오류로 보존하고 자동 강등하지 않는다.
- `DungeonSystem`은 새로 생성하는 해당 두 template 인스턴스의 regionTier9/10에만 명시적 변형 ID를 고정한다. 다른 생태/건물은 기존 원형 규칙을 유지한다. 기존에 탐험·저장한 원형 던전은 사후 변형하지 않는다. UI는 지역난도/전투티어/변형이름을 구분한다.
- 보상 청구 키는 기존 world/dungeonInstance/boss channel을 유지하고, contentVariantId로 새 청구키를 만들어 중복 보상을 열지 않는다. 인스턴스에 고정된 rewardRef로만 재시도한다.

## 구현 상태와 완료 기준

BossSystem은 명시 ID를 통한 원형 정의 해석, 실제 재배치, 영속 `variantState`, 보스 채널 보상 override를 구현한다. DungeonSystem은 새 T9/T10 인스턴스만 해당 ID에 고정하고 기존 인스턴스는 원형으로 유지해야 한다. 실행 완료 판정은 네 변형의 실제 3페이즈 순회, 8원형 불변, 기관 파손 fallback, 기술별 EU·피해 예산, 기믹별 이동 전환, 차폐·출구·3D 회피, 활성 cast·재배치 저장 복구, 보상 중복 방지 검증을 요구한다. 최소 T9 수호자/T10 파수기 실제 플레이와 장구 DPS/TTK 측정 전에는 제안 수치의 밸런스가 검증됐다고 표시하지 않는다.
